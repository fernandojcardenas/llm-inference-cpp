M7 load test: tools/loadtest_server.py against a real llmi-server
===================================================================
Model: models/smollm2-135m-instruct (the real model, not a synthetic test
fixture). Server: llmi-server models/smollm2-135m-instruct --port 8104
--max-concurrent 4 (the server's default concurrency limit). Each run issues
16-24 requests both sequentially (concurrency=1, the baseline) and
concurrently, non-streaming and streaming.

Run 1: --concurrency 4 --requests 16 --max-tokens 24 (at the server's
concurrency limit, so every request is accepted)
-------------------------------------------------------------------------
sequential (concurrency=1):   mean latency 1.233s  (16/16 succeeded)
concurrent (concurrency=4):   mean latency 4.020s  (16/16 succeeded)
concurrent streaming (conc=4): mean latency 3.689s, mean time-to-first-byte
                                2.964s (16/16 succeeded)

mean latency grew 3.26x going from concurrency=1 to concurrency=4.

This is exactly what ADR 0008 predicts: with one generation slot serializing
every request's actual token generation, four requests submitted at once
do not run four times as fast in aggregate -- each one queues behind the
others, so per-request latency grows roughly in proportion to how many
requests are competing for the one slot (3.26x at 4-way concurrency, not
the ~1x a server with true parallel generation would show). Throughput
(total tokens generated per wall-clock second) stays essentially flat
between the sequential and concurrent runs; only where each individual
request's time goes changes, from "running" to "running plus queued
behind peers."

Run 2: --concurrency 8 --requests 24 --max-tokens 24 (above the server's
concurrency limit, to exercise the 429 path for real)
-------------------------------------------------------------------------
sequential (concurrency=1):    mean latency 1.090s  (24/24 succeeded)
concurrent (concurrency=8):    status counts {200: 4, 429: 20}
concurrent streaming (conc=8): mean latency 7.751s  (24/24 succeeded --
                                see note below)

With 8 concurrent non-streaming requests against a concurrency limit of 4,
exactly 4 succeeded and 20 were rejected with 429 and the documented error
body:
  {"error":{"message":"server is at its concurrent request limit",
            "type":"rate_limit_error"}}
4 is exactly the configured --max-concurrent value: the bounded-queue design
in ADR 0008 is not an approximation, it is an exact admission-control count.

The streaming phase of the same run shows 24/24 succeeding rather than the
same 429 pattern: tools/loadtest_server.py runs its non-streaming and
streaming phases one after another, not interleaved, so by the time the
streaming phase starts, every non-streaming request from the previous phase
has already completed and the in-flight counter is back at zero -- this
load test measures each phase's own concurrency, not sustained combined
load. Measuring genuinely mixed streaming/non-streaming concurrent load
(and a sustained-overload run long enough to see the 429 rate stabilize) is
natural follow-up work, not required to demonstrate either of ADR 0008's
two claims: that a single generation slot makes latency -- not throughput --
scale with concurrency, and that the bounded queue turns "accept unboundedly
and let requests wait forever" into "accept up to a declared limit, reject
the rest immediately and explicitly."
